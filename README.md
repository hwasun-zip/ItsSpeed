# 잇츠스피드 (ItsSpeed)
### 머천트 카탈로그 요청 처리 프로세스 병목 분석 & SLA 자동 모니터링

> ⚠️ 실제 특정 기업의 서비스나 내부 데이터와 무관한 개인 학습 프로젝트입니다.
> 실무 운영 데이터가 없어, 공개 CS 티켓 데이터의 시간 분포를 참고하고
> 카탈로그 운영 도메인 지식(검수 난이도, 반려 사유, SLA 민감도)을 반영해
> 합성 데이터를 직접 설계하고 생성했습니다. (근거는 아래 "데이터 설계" 참고)

---

## 왜 이 분석인가

배달 플랫폼에서 상점(머천트)이 메뉴, 이미지, 가격, 영업시간 등을 수정 요청하면,
운영팀은 이를 접수 → 검수 → 반영까지 처리합니다.
이 과정이 느리거나 반려가 반복되면 **상점 불만**으로 이어지고,
특히 영업시간/휴무일처럼 **매출에 즉시 영향을 주는 요청**은 처리 지연이 곧 기회비용입니다.

이 프로젝트는 "요청 유형에 따라 병목의 성격이 다르다"는 가설을 세우고,
SQL로 그 차이를 정량적으로 규명한 뒤, 반복되는 진단을 자동화하는 것까지 구현했습니다.

## 데이터 설계

실제 운영 데이터가 없어 두 가지를 결합해 재현했습니다.

1. **시간 분포의 현실감**: 공개 CS 티켓 데이터에서 관찰되는 리드타임 분포 형태(오른쪽 꼬리가 긴 로그정규분포)를 참고
2. **도메인 로직**: 요청 유형별 특성을 아래와 같이 의도적으로 차등 설계

| 요청 유형 | 설계 의도 | 근거 |
|---|---|---|
| 이미지 교체 | 리드타임 김 | 화질/규격 등 시각적 검수는 텍스트 검수 대비 판단 시간이 오래 걸릴 것이라 가정 |
| 가격 수정 | 반려율 높음 | 원부자재와 메뉴판 표기 대사 확인이 필요해 1차 검수 통과율이 낮을 것이라 가정 |
| 영업시간/휴무일 변경 | 주말 SLA 단축 | 배달 매출에 즉시 영향을 주므로 금~일 접수 시 SLA를 24h→2h로 단축 |
| 신규 메뉴 등록 | 중간 특성(대조군) | 검수와 반려 모두 평균적 수준으로 설정 |
| 메뉴 설명 수정 | 가장 여유 | 텍스트 수정 위주로 검수 난이도가 낮다고 가정 |

절대적인 수치(예: "왜 하필 3.4시간인가")에는 실측 근거가 없습니다.
분석의 초점은 **유형 간 상대적 격차와 그로 인한 병목 패턴**에 있습니다.
노이즈(분산)를 충분히 반영해 극단적으로 깔끔한 결과가 나오지 않도록 설계했습니다.

- 데이터 규모: 6,000건 (2026.01 ~ 2026.06), 상점 900개, 담당자 12명
- 도구: Python(numpy, pandas), SQLite(SQL 분석), matplotlib(시각화)

## 분석 설계 및 핵심 발견

### 1. 요청유형별 처리시간(TAT) — "얼마나 걸리나"

윈도우 함수(`NTILE`)로 평균과 중앙값을 함께 산출해 극단값에 의한 착시를 줄였습니다.

| 요청유형 | 평균(h) | 중앙값(h) |
|---|---|---|
| 이미지_교체 | **44.0** | **37.0** |
| 신규_메뉴_등록 | 22.8 | 19.8 |
| 가격_수정 | 21.3 | 17.8 |
| 영업시간_휴무일_변경 | 12.5 | 10.8 |
| 메뉴_설명_수정 | 9.1 | 8.0 |

→ **이미지 교체가 2위 대비 약 2배 느림.** 검수 난이도 자체가 병목.

### 2. SLA 위반율 (요일 가중 포함) — "약속을 지켰나"

| 요청유형 | 접수구분 | 적용SLA(h) | 위반율(%) |
|---|---|---|---|
| 영업시간_휴무일_변경 | 평일 | 24 | 5.8 |
| 영업시간_휴무일_변경 | **주말** | **2** | **100.0** |
| 가격_수정 | 평일/주말 | 12 | 71~75 |
| 이미지_교체 | 평일/주말 | 48 | 32~33 |

→ 영업시간 변경 요청의 **실제 처리시간 최솟값이 3.5시간**인데 주말 SLA는 2시간으로 설정돼 있어,
현재 프로세스 구조로는 **SLA 자체가 물리적으로 달성 불가능**한 상태임을 확인.
"프로세스 단축"이 아니라 **SLA 재설정 또는 주말 전담 패스트트랙**이 필요한 문제.

### 3. 재반려(핑퐁, rework_count≥2) — "왜 오래 걸리는가의 원인"

상점-운영팀 간 반려가 2회 이상 반복되는 "핑퐁" 구간을 별도 정의해 진단했습니다.

| 요청유형 | 핑퐁비율 | 핑퐁건 평균(h) | 일반건 평균(h) | 배수 |
|---|---|---|---|---|
| 가격_수정 | **13.0%** | 43.2 | 18.1 | 2.4배 |
| 신규_메뉴_등록 | 5.1% | 47.1 | 21.5 | 2.2배 |
| 이미지_교체 | 2.8% | 76.7 | 43.1 | 1.8배 |

→ 가격 수정은 TAT 자체는 중간 수준이지만, **핑퐁이 걸리면 처리시간이 2.4배로 급증**.
SLA 위반율(70%대)과 핑퐁 비율이 동시에 1위라는 점에서, 가장 시급한 개선 대상으로 판단.

### 4. 담당자별 처리량/반려율 — "사람 문제인가, 구조 문제인가"

반려율 14.0%~23.9% 사이로 완만하게 분포, 팀 평균(19.2%) 대비 이상치로 볼 담당자는 없음.

→ 특정 개인의 역량 문제가 아니라 **요청 유형과 SLA 정책 자체의 구조적 문제**라는
1~3번 결론에 확신을 더해주는 배제(rule-out) 근거로 활용.

## 자동화 — SLA 모니터링 & 주간 리포트

위 4가지 분석을 매주 자동으로 반복 진단하도록 구현했습니다.

- `generate_action_items()`: Rule-based로 임계치 초과 항목을 자동 탐지해 액션 문장 생성
  - 예) 요청유형 평균 TAT > 30h → "자동 검수 도구 도입 검토 권장"
  - 예) 주말 SLA 위반율 ≥ 90% → "SLA 정책 자체 재검토 필요" (정책-현실 괴리 탐지)
  - 예) 핑퐁 비율 > 10% → "접수 단계 필수 조건 명확화 필요"
  - 예) 담당자 반려율 > 팀평균×1.2 → "업무 배정 재점검 권장" (표본 수 주의 문구 포함)
- `generate_weekly_report()`: 지정 기간의 지표 요약 + 액션 아이템을 마크다운 리포트로 생성
- `schedule` 라이브러리로 "매주 월요일 9시 실행" 로직 시연
  - 실제 운영 배포 시나리오: 로컬/사내 배치 서버에 스크립트 이관 후 crontab 등록
  ```
  0 9 * * 1 /usr/bin/python3 /path/to/weekly_report_generator.py
  ```

## 시각화

- 요청유형별 평균 TAT 막대그래프 (이미지_교체 병목 강조)
- SLA 위반율 평일 vs 주말 그룹 막대그래프 (정책-현실 괴리 시각화)
- 주차별 SLA 위반율 추이선 (6개월간 평균 37% 내외로 등락 → 일시적 이슈가 아닌 만성적 구조 문제임을 뒷받침)

## 실행 방법

1. `ItsSpeed.ipynb`를 Google Colab에서 엽니다.
2. 위에서부터 순서대로 실행하면 데이터 생성 → SQL 분석 → 자동 리포트 → 시각화까지 진행됩니다.
3. 한글 폰트 셀(나눔고딕 설치)은 최초 1회 실행 후 런타임 재시작이 필요할 수 있습니다.
